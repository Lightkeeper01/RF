# 组织与项目诊断

## 一、为什么我们总是被客户牵着走？

### 根因分析

被客户牵着走，表面上是"客户需求变了"，本质上是**公司内部没有产品定义的主权**。

| 层级 | 应有的职责 | 当前实际状态 | 后果 |
|------|-----------|-------------|------|
| 市场/销售 | 收敛客户需求，判断客户角色（终端/方案商/中间商），确定产品线归属 | 将客户原话直接转给研发，未做需求过滤和分类 | 研发承接了"需求理解"职责 |
| 产品管理 | 定义产品规格边界，冻结需求，发布 PRD/技术规格书 | 基本缺失或不到位，没有需求冻结机制 | 需求随客户沟通不断漂移 |
| 研发 | 在冻结需求下给出技术方案，明确技术边界 | 被迫同时做需求理解、方案判断、成本解释 | 研发精力严重分散，技术深度下降 |
| 工艺 | 明确给出工艺能力边界（POR），区分量产能力与样品能力 | 被动配合，未能主动输出工艺能力边界文件 | 研发无法依据工艺边界做出承诺 |
| 测试 | 独立分析失效根因，给出有结论的测试报告 | 只输出数据和曲线，无法独立做根因分析 | 研发需补位做失效分析 |
| 项目管理 | 管理需求变更，识别重大变更并触发项目评审 | 未建立需求变更管理机制，所有变更在同一个项目中累积 | 项目范围无限扩大，资源无法聚焦 |

### 本质结论

> **公司尚未形成"市场定义需求 → 产品定义边界 → 研发给出技术判断 → 项目管理做资源取舍"的完整价值链。**

结果是：客户的每一句话都能直接穿透到研发，研发成了公司唯一的"问题缓冲区"。

## 二、为什么各团队没有形成清晰边界，最后都压到研发？

### 原因层次分析

**第一层：流程缺失**
没有明文的"需求收敛 → 产品规格冻结 → 研发接口"流程。没有流程，就没有责任边界，也没有交接节点。

**第二层：能力不对等**
市场/销售不具备技术判断能力 → 只能传话；
测试团队不具备失效分析能力 → 只能给数据；
工艺团队未主动输出能力边界文件 → 研发只能自己摸。
能力短板自动让研发来填。

**第三层：激励机制**
研发团队（尤其是技术牵头人）的绩效往往与"项目推进""客户满意度"挂钩，导致主动补位反而成为默认行为，组织没有动力修复流程问题。

**第四层：管理层没有明确切割**
如果领导层没有明确要求各职能对自己的输出负责（市场需出需求分析报告，工艺需出能力边界文件，测试需出根因分析报告），各团队就会默认"研发能搞定"，久而久之形成路径依赖。

## 三、如果继续补位所有方向，会有什么后果？

### 对个人

| 后果 | 说明 |
|------|------|
| 精力分散，技术深度下降 | 同时做技术、产品、市场、失效分析，每件事都做不到最好 |
| 成为"稳压器"而非"价值创造者" | 补位系统漏洞不会被认可为核心贡献，反而成为理所当然 |
| 倦怠和流失风险 | 长期承担超出角色边界的责任，缺乏成就感，职业发展路径不清晰 |
| 决策责任与决策权不匹配 | 承担了很多判断责任，却没有相应的资源调配权和决策权，形成"责任陷阱" |

### 对团队

| 后果 | 说明 |
|------|------|
| 其他团队能力持续萎缩 | 测试、工艺、市场都知道"研发会补"，缺乏提升动力 |
| 研发成为瓶颈 | 所有问题都收口到研发，研发成为组织的限速步骤 |
| 技术判断权威性下降 | 研发忙于补位，对技术决策缺乏深度思考，判断质量下降，逐渐失去内部信任 |

## 四、如何从"我来补位"切换到"我定义边界，让各团队按边界负责"？

### 第一步：把"补位"行为显性化

在内部会议或汇报中，每次补位时都明确说出：
> "这件事本来应该由 XX 团队提供输入，但因为没有，我今天临时补了。这是一次例外，不是常态。"

将隐性补位变成显性记录，让管理层看到系统性问题。

### 第二步：定义各团队的标准输出物（deliverable）

提出并推动建立以下输出物标准：

| 团队 | 应输出的标准文件 | 触发时机 |
|------|----------------|---------|
| 市场/销售 | 客户需求分析报告（含客户角色、需求分类、产品线归属建议） | 客户提出新需求时 |
| 产品管理 | 产品规格书（PRD）+ 需求冻结确认单 | 项目启动前 |
| 工艺 | 工艺能力边界文件（POR，含承诺指标与不承诺指标） | 项目立项时 |
| 测试 | 含根因分析结论的测试报告（不只是数据和曲线） | 每轮测试完成后 |
| 项目管理 | 需求变更评审记录 + 变更影响分析 | 客户提出变更时 |

### 第三步：在项目会议中推动需求分流

当客户同时提出路线 A 和路线 B 的需求时，明确提出：
> "这两条需求对应不同的产品线，需要分开立项、分开评估、分开定价。我们今天的会议需要先明确我们讨论的是哪条路线。"

### 第四步：建立"研发拒绝接单"的合理机制

当市场/销售未提供需求分析，直接把客户需求推给研发时，可以通过邮件/内部工单方式回复：
> "研发收到该需求，但在启动技术评估前，需要市场提供：（1）客户角色确认；（2）产品线归属；（3）初步商业规模判断。请市场团队在 X 日前提供。"

这不是拒绝协作，而是要求前置输入到位。

## 五、需求变更管理：从 800 Mbps 到 5620，应如何处理？

当客户需求从路线 A（800 Mbps 单端）升级到路线 B（64 Gbps 差分）时，这是**重大需求变更（Major Change Request）**，应触发以下动作：

1. **项目管理登记需求变更**，评估对进度、资源、成本的影响。
2. **研发给出技术可行性初步判断**（不是详细方案，只是"能/不能/需要多久"）。
3. **市场确认客户愿意为新需求支付新的价格**，而不是用旧项目的价格逻辑来套新性能。
4. **管理层决策**：是在原项目内变更，还是新开一个项目/产品线。

**如果项目管理不做这一步，研发就会被强迫在一个项目里同时做两件事，资源和注意力都会被稀释。**
