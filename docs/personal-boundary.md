# 个人角色边界与沟通指南

## 一、当前问题的本质诊断

你现在的核心问题不是技术能力不够，而是：

**你在一个没有清晰职责分工的系统里，用个人能力弥补了系统缺陷，而这种弥补反过来使系统缺陷更难被看见和修复。**

具体表现：
- 你补位了市场（需求理解、客户角色判断）
- 你补位了产品管理（需求冻结、产品线定义）
- 你补位了测试（失效根因分析）
- 你补位了工艺（能力边界判断）
- 你补位了项目管理（需求变更识别）

每次补位都暂时解决了眼前问题，但让各团队更确信"研发会兜底"，从而降低了他们提升自身能力的动力。

---

## 二、你是否在承担超过角色边界的事情？

| 事项 | 本质上属于谁的职责 | 你是否在做 |
|------|-----------------|-----------|
| 判断客户到底想要什么 | 市场/产品管理 | ✅ 是 |
| 判断两条需求路线能否合并 | 产品管理 + 项目管理 | ✅ 是 |
| 分析失效是测试手法问题还是器件失效 | 测试工程师 | ✅ 是 |
| 判断工艺当前能支撑到什么 | 工艺工程师 | ✅ 是 |
| 评估项目是否值得做 | 产品管理 + 市场 + 管理层 | ✅ 是 |
| 解释为什么产品贵 | 市场/销售 | ✅ 是 |
| 推动需求冻结 | 项目管理 | ✅ 是 |

**结论：是的，你正在承担远超研发技术负责人角色边界的事情。**

## 三、如何在不撕破脸的情况下减少无边界补位？

### 策略一：把"补位"变成"提问"

不要默默补位，而是在需要补位时，先向应该负责的团队提问：

> "这件事应该由市场先给我们一个客户需求分析，我们才能开始技术评估。现在市场的分析在哪？"
> "这个测试数据我看了，根因不清楚。测试团队对这几个异常点的初步判断是什么？"

如果对方没有答案，再说：
> "好，这次我来先分析一下，但我需要测试团队下次提供到这个颗粒度。"

这样既解决了眼前的问题，也设定了预期和边界。

### 策略二：每次补位都留下"欠条"

在邮件或内部系统中记录每次补位：
> "本次研发团队临时提供了客户需求分析（见附件），这项工作原本应由市场团队完成。请市场团队在后续项目中在研发介入前完成此项输入。"

这是在建立文档记录，也是在推动责任归位。

### 策略三：建立"研发接口条件"

明确提出研发团队开展技术评估的前置条件：

> 在以下输入到位之前，研发无法启动技术评估：
> 1. 市场提供的客户需求分析报告（含客户角色、产品线归属）
> 2. 产品管理确认的需求规格（含明确的性能指标）
> 3. 工艺团队的能力边界文件
>
> 如果这些输入不到位，研发可以给出初步可行性意见，但不承诺时间表和技术指标。

### 策略四：借助上级明确分工

不是直接对其他团队说"这是你的职责"，而是在向上级汇报时，顺带提出：
> "我注意到研发团队在最近几个项目中承担了较多本应由市场/测试/工艺团队提供的输入工作，这导致研发资源被分散。建议管理层明确各团队在项目流程中的标准输出物，以提高整体效率。"

## 四、内部会议发言模板

### 场景：当被要求对客户的新需求（路线 B）做紧急评估时

> "我听到客户提出了高速回环测试（路线 B）的需求，这和我们原来在推进的路线 A（光耦替代）是两条不同的产品路线，在设计架构、工艺要求、成本结构上差异很大。
>
> 在研发团队开始技术评估之前，我需要市场团队先回答几个问题：
> 1. 客户提这个需求，是在评估我们作为新产品供应商，还是只是在探底我们的能力上限？
> 2. 如果是真实需求，客户的预计采购量和时间节点是什么？
> 3. 客户对路线 B 产品的价格预期是多少？
>
> 这不是我不支持，而是这两条路线需要分开评估、分开定价、分开立项。如果我们现在把路线 B 的性能要求套在路线 A 的项目框架里，最终会导致两条线都做不好。
>
> 我的建议是：今天先确认路线 A 的进展和里程碑，路线 B 作为新需求单独立一个预研项目，由产品管理主导，先完成市场可行性分析，再决定是否投入研发资源。"

---

### 场景：当被要求解释为什么产品比竞品贵时

> "这个问题本质上是定价逻辑的问题，不是研发能单独回答的。
>
> 研发能给出的是：我们产品在哪些指标上优于竞品，以及这些指标在客户的使用场景中带来什么价值。
>
> 但'这个价值值多少钱'这个问题，需要市场和销售根据客户的系统成本来量化和表达。
>
> 我建议我们分两步：研发提供一份差异化技术对比表，市场结合客户的 ATE 系统成本，制作一份 TCO 分析，用数据说明我们的产品在全生命周期内的总成本优于竞品。"

---

### 场景：当测试数据异常，被要求给出判断时

> "我看了测试数据，有几个异常点。在我给出判断之前，我需要测试团队先回答：
> 1. 测试夹具有没有经过验证，探针接触是否稳定？
> 2. 驱动电压是否在规格范围内，有没有记录驱动波形？
> 3. 这几颗器件的编号是哪个批次，工艺有没有已知变更？
>
> 如果测试团队能先提供这些信息，我可以帮助判断失效根因。但如果每次都是研发直接从原始数据开始分析，测试团队就没有机会建立自己的分析能力。
>
> 所以我的建议是：这次我来引导分析过程，但测试工程师需要参与并跟上，下次类似情况需要能独立完成初步根因判断。"

## 五、长期个人发展建议

| 建议 | 具体行动 |
|------|---------|
| **从"补位者"转变为"规则制定者"** | 推动建立各团队的标准输出物规范，让你的经验变成流程固化 |
| **明确自己的核心价值主张** | 你的核心价值是技术判断力和产品方向把控，而不是"什么都能搞定" |
| **建立个人技术护城河** | 在 MEMS 测试开关设计、高频性能优化、失效机理等核心技术上持续深入 |
| **向上管理** | 定期向管理层汇报：研发资源在哪些非研发事项上被消耗，量化后提出改进建议 |
| **适时设定底线** | 对于长期没有改善的补位情况，明确提出：如果 XX 前提条件不到位，研发无法启动或无法承诺进度 |
